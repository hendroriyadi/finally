### Claude's-discretion choices made here

| Question | Choice | Rationale |
|---|---|---|
| Spec file naming | Numeric-prefixed: `01-fresh-start`, `02-watchlist`, `03-trading`, `04-portfolio-viz`, `05-chat`, `06-sse-reconnect` | Playwright collects spec files in alphabetical order. With the unprefixed names `05-RESEARCH.md` sketches, `chat.spec.ts` would run before `fresh-start.spec.ts` — and the fresh-start scenario is the only one that asserts an untouched $10,000 balance, so it would fail after the chat spec had already spent money. The prefix makes the one real ordering dependency in this suite explicit and enforced rather than incidental |
| Whether specs depend on each other's leftovers | Only spec 01 depends on order; every other spec establishes its own preconditions | The visualization spec buys its own position rather than relying on the trading spec leaving one; the watchlist spec removes whatever it adds. One declared ordering dependency is a design; six implicit ones are a haunted house |
| Parallelism | `fullyParallel: false` with a single worker | All specs share one SQLite database inside one app container. Concurrent workers would race on cash and positions and produce failures that look like product bugs |
| How the app is made ready before tests run | Docker's `HEALTHCHECK` plus Compose's healthcheck-gated `depends_on` | Exactly what that feature exists for. A hand-written polling loop wrapping `compose up` duplicates it and gets the readiness definition subtly wrong |
| Whether the app service mounts a data volume | No — the container's database is container-local and dies with it | The fresh-start scenario needs a genuinely fresh, freshly-seeded database. Persistence is DEPLOY-02's claim and is proven separately by `test/verify-persistence.sh`; mounting a volume here would make spec 01 depend on whatever the last run left behind |
| Teardown | Every documented run ends with a Compose `down -v` | Compose leaves stopped containers in place after `--exit-code-from`, so a second `up` would reuse the first run's app container and its already-mutated database. The teardown is what makes the suite repeatable, and it is part of the command, not an afterthought |
| Report output path | `./artifacts/report`, relative to the config file | `05-RESEARCH.md`'s sketch writes `../test/artifacts/report`, which resolves to the same place because Playwright resolves config paths relative to the config's own directory — but it reads as though it escapes `test/`, and the next person to edit it will get it wrong. Same destination, unambiguous spelling |
| Whether the suite can also run outside Compose | Yes — the base URL reads an environment variable and falls back to localhost on port 8000 | Lets a developer with a container already running from `scripts/start_mac.sh` iterate on a single spec in seconds instead of rebuilding an image. Costs one line |
| Waiting for live-updating UI | Playwright's auto-retrying assertions, with explicit generous timeouts where the stream is involved | Prices arrive on the stream's own cadence, not in response to anything the test did. A fixed wait is both slower and flakier than an assertion that polls until the condition holds |
| Whether production components gain test hooks | No | No file outside `test/` is in `files_modified`. Every locator anchors on a heading, an accessible name, or a placeholder that already exists, so the suite tests the shipped UI rather than a UI adapted to be testable |

## The canonical command

```bash
docker compose -f test/docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from playwright
docker compose -f test/docker-compose.test.yml down -v
```

The first line is `05-VALIDATION.md`'s automated command for TEST-04, verbatim. The second is the
teardown that makes it repeatable; it must run whether the first line passed or failed, and the suite's
exit code is the first line's.
