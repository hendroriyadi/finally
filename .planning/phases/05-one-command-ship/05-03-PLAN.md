### Claude's-discretion choices made here

| Question | Choice | Rationale |
|---|---|---|
| Framework (D-11 leaves it open) | Vitest 4.1.10 + React Testing Library 16.3.2 + jsdom 30.0.1, per this repo's bundled `next/dist/docs/01-app/02-guides/testing/vitest.md` | The guide ships inside the installed Next.js 16.2.12, so it is version-exact rather than remembered. Jest would need Babel/ts-jest wiring for this TS/ESM stack that Vitest gets from Vite for free |
| How modules are replaced in tests | `vi.mock("@/lib/api", ...)` with `importOriginal`, **not** `vi.spyOn(api, ...)` | `05-RESEARCH.md`'s Pattern 4 sketch uses `vi.spyOn` on an imported module namespace. ES module namespace objects are sealed, so that call throws rather than patching. `vi.mock` with a factory that spreads the original is the working form, and spreading the original is what keeps `ApiError` the real class so the components' `instanceof` branches still behave |
| Whether `globals: true` is set | No — every test imports `test`, `expect`, `vi`, `beforeEach` from Vitest explicitly | Implicit globals would need a `types` entry in `tsconfig.json`, widening a change this plan wants to keep additive. Explicit imports also make each test file self-describing |
| Whether the context providers are rendered for real | No — the two context hooks are module-mocked | `PriceStreamProvider` constructs an `EventSource`, which does not exist in jsdom, so rendering it for real fails at mount for a reason that has nothing to do with the component under test. Mocking the hook keeps each test about one component |
| Test file location | Colocated: `frontend/components/<Component>.test.tsx` | Matches the paths `05-VALIDATION.md` already names in its automated commands, and matches Vitest's default include glob with no extra config |
| Whether `tsconfig.json` is modified | Yes, minimally: the test globs and the two Vitest filenames are appended to the existing `exclude` array | The Next.js `include` glob matches every `.tsx` file, so without this `next build` would type-check the test files — and `npm run build` is the first instruction of the Docker image's frontend stage. Vitest transpiles with esbuild and does not type-check, so nothing is lost. This keeps the production build unaffected by test tooling |
| `@vitest/coverage-v8` | Installed | `05-RESEARCH.md`'s Validation Architecture documents `npx vitest run --coverage` as the frontend full-suite command; omitting the provider would make that documented command fail. Same repository and same audit disposition as `vitest` itself |
| Package legitimacy gate handling | Automated live-registry re-verification before install, plus a recorded end-of-phase human confirmation — **not** a mid-plan blocking checkpoint | Two concrete reasons. `.planning/config.json` sets `human_verify_mode: "end-of-phase"`, which replaces mid-plan human checkpoints with end-of-phase checks. And this project already has a precedent for exactly this situation: Phase 3's `recharts` install was gated by re-verifying the package directly against the live npm registry rather than trusting the research citation (`.planning/STATE.md`, Phase 3 03-02). All flagged packages here carry the same `too-new` false-positive signature — a routine recent release of a package with 30M-90M weekly downloads, an official GitHub repository, and a null `postinstall` — and the re-verification below re-establishes each of those facts live rather than citing them |
| Which components get tests beyond the four named areas | None | TEST-03 names four areas; four files cover them. `PortfolioHeatmap`, `PnLChart`, and `DetailChart` are Recharts-driven SVG whose meaningful assertions are visual, and Plan 05-04's browser suite covers them where they can actually be seen |
