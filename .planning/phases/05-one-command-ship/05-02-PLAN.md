### Claude's-discretion choices made here

| Question | Choice | Rationale |
|---|---|---|
| How "idempotent" is implemented for start | Anchored name filter (`name=^finally$`) to detect a running container; if one is running, print the URL and exit; otherwise force-remove any *stopped* container of the same name, then run | `docker ps --filter name=X` is a **substring** match, so an unanchored filter would also match `finally-verify-1` from Plan 05-01's persistence script and report the app as already running when it is not. The force-remove-then-run branch is what makes a crashed-and-exited container recoverable without the user learning `docker rm` |
| Whether `--restart` is set on the container | No | It would make the container survive a Docker daemon restart, which reads as the app "coming back on its own" and is a surprise nobody asked for. `planning/PLAN.md` §11's canonical command does not include it |
| Where the scripts resolve the repo root from | The script's own location (`dirname` of the script path, then up one), followed by an explicit change of directory | `docker build .` and `--env-file .env` are both relative to the working directory, so a script invoked as `./scripts/start_mac.sh` from the repo root and one invoked by absolute path from elsewhere must behave identically |
| Whether stop removes the image | No — container only | Removing the image would make every subsequent start rebuild from scratch, turning a stop/start cycle from seconds into minutes. `planning/PLAN.md` §11 asks only that the volume survive |
| Whether the Windows scripts get a `checkpoint:human-verify` task | No — a `<verify><human-check>` entry instead | `.planning/config.json` sets `human_verify_mode: "end-of-phase"`, which replaces mid-plan human checkpoints with end-of-phase human checks. The `.ps1` pair is verified structurally here (mirror parity against the `.sh` pair, which *is* executed) and behaviorally by a human on Windows at the phase gate — `05-VALIDATION.md`'s "Manual-Only Verifications" table already records this as the phase's single manual item |
| Whether a README quick-start is added | Yes, a short section | The phase goal is "anyone can run the entire workstation with a single command"; a command nobody can find does not satisfy it. Scoped to a few lines naming the four scripts and the URL — no restructuring of the existing document |
| Whether `docker compose` is used by these scripts | No | `05-RESEARCH.md` Pitfall 9: Compose has a v1/v2 CLI split that would need detection logic, and the production path needs only `docker build` and `docker run`. Compose appears exactly once in this phase, in Plan 05-04's test-only file |

    Implements D-08, D-09, D-10, D-18.

    **`.env.example`** — new file at the repo root. Exactly the three keys from `planning/PLAN.md` §5,
    each with an empty or default value and a one-line comment above it explaining what happens when it
    is left as-is: the copilot's chat calls fail gracefully into their fallback reply without the
    OpenRouter key; the built-in simulator runs when the Massive key is empty; the mock-LLM flag stays
    off unless the E2E suite turns it on. No other keys.

    Three formatting constraints, because this file is consumed by Docker's `--env-file` parser and not
    by a shell: values must be unquoted (quotes become part of the value, so a quoted key would be sent
    to OpenRouter with the quote characters attached); comments must occupy whole lines, never trail a
    value on the same line; and no value may be a real credential — this file is committed, and it is
    the one file in this phase where a copy-paste of a working key would publish it.

    **`scripts/start_mac.sh`** — new file, `#!/usr/bin/env bash` and `set -euo pipefail`. Despite the
    name it must work on Linux too (`planning/PLAN.md` §4 pairs macOS and Linux on this script).

    Declare the four shared identifiers as variables at the top, each with an environment-variable
    override and the documented default: image tag `finally:latest`, container name `finally`, volume
    name `finally-data`, host port 8000. Resolve the repository root from the script's own path rather
    than the caller's working directory and change into it, so the relative `docker build .` and
    `--env-file .env` below mean the same thing no matter where the script was invoked from.

    Parse two optional flags — one that forces a rebuild and one that opens a browser — and reject
    anything else with a usage line and a non-zero exit. Then check the two Docker preconditions
    separately and report them differently, because they have different fixes: the CLI not being
    installed at all, and the CLI being present while the daemon is not running. A student whose Docker
    Desktop is closed should be told to open Docker Desktop, not told to install Docker.

    The environment-file fallback (D-10) comes next and before anything that could fail because of it:
    if no `.env` exists, copy `.env.example` to `.env` and print a line telling the user a starter file
    was created and which key to fill in to enable the copilot. This is the single most important
    branch in the file — `--env-file` exits with a hard Docker error when the file is absent, `.env` is
    gitignored so no fresh clone has one, and that error on a first-ever run is exactly the experience
    this phase exists to eliminate.

    Build conditionally: if the rebuild flag was passed, or if inspecting the image tag fails, run
    `docker build` with that tag from the repository root. Otherwise skip the build — a start that
    rebuilds every time is not the fast second run idempotence is supposed to give.

    Then the idempotency branch. Query for a *running* container using an **anchored** name filter, so
    the pattern matches the container name exactly rather than as a substring. If one is running, print
    that the app is already running and fall through to the URL output without touching it. Otherwise,
    force-remove any container of that name first — tolerating absence — and then `docker run` it
    detached, with the named volume mounted at the container's database directory, the host port
    published to the container's 8000, and the environment file passed. Removing before running is what
    recovers from a container that exited or crashed: without it, the second invocation fails with a
    name-conflict error, which is precisely the non-idempotent behavior the requirement forbids.
    Suppress the container-id echo `docker run` prints; the URL is the useful output.

    Finish by printing the URL, and opening it in a browser only when the open flag was passed, trying
    the macOS opener first and the Linux one as a fallback, tolerating both being absent.

    **`scripts/stop_mac.sh`** — new file, same shebang and strict mode, same variable block and same
    Docker precondition checks. Query for a container of that name including stopped ones, again with
    an anchored filter. If one exists, force-remove it and report that it was stopped and removed; if
    none exists, report that nothing was running — and exit 0 in both cases, because a stop script that
    fails when the app is already stopped is not idempotent.

    Then print, as the last line, that the named data volume was left in place and that the user's cash,
    positions, and history are safe. The script must never invoke Docker's volume-removal verb or pass
    the flag that makes container removal take anonymous volumes with it — a stop that silently deleted
    a user's portfolio would be the worst bug this phase could ship. That prohibition is enforced by a
    comment-stripped negative grep in the verify command, so express the rationale in the closing
    message rather than restating the forbidden command in a comment.

    Make both scripts executable.

    **Then prove it, in this order, and report each observation:**

    First the fresh-clone path, carefully. Copy the existing `.env` to a temporary location *outside
    the repository* (it holds the developer's real key), move it aside, run the start script, and
    confirm it printed the starter-file message and that a `.env` now exists carrying the three keys.
    Then delete the generated `.env` and restore the original from the temporary copy, and confirm the
    restored file is byte-identical to what was there before by comparing checksums. Do not skip the
    checksum comparison — this is the one step in the phase that touches a file holding a live
    credential.

    Then the idempotence proof: run the start script twice in a row, assert exactly one container with
    the anchored name filter, and — because a container existing is not the same as an app working —
    poll `/api/health` on the published port until it answers. Then run the stop script twice in a row,
    assert zero containers with the same anchored filter, and assert the named volume still exists.
    Leave the volume in place; that is the correct end state and it is what a real user would have.

    **`scripts/start_windows.ps1`** and **`scripts/stop_windows.ps1`** — direct translations of the two

    Four PowerShell specifics that are easy to get wrong and would each produce a script that looks
    correct and misbehaves:

    A `param` block declaring the two switches must be the first executable statement in the file —
    only comments may precede it. Put the header comment above it and everything else below it.

    Setting the error-action preference to stop does **not** make a failing native command throw.
    `docker` is a native command, so after every `docker` invocation whose failure matters, test
    `$LASTEXITCODE` explicitly and exit non-zero. This is the single most common way a PowerShell port
    of a `set -e` script silently continues past a failed build.

    Resolve the repository root from `$PSScriptRoot`'s parent and set the location there, matching the
    shell scripts' behavior for the same reason.

    Use PowerShell's own file test and copy for the environment-file fallback, and its own
    process-start call to open the browser. Do not shell out to `cmd`.

    Both files should carry a short header comment stating that they mirror the `.sh` pair, that the
    shell pair is the one automatically verified in this project's environment, and that the two must
    be changed together — so a future edit to one does not silently create a platform where the app
    behaves differently.
