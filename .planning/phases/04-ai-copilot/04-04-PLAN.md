<objective>
Give the copilot a face. Everything behind the wire works — a message reaches a model, its answer moves real money, and the whole exchange is written down. None of it is reachable from a browser.

This plan builds the docked AI Copilot panel `04-UI-SPEC.md` specifies: a 384px right-hand dock on a wide screen that collapses to a 56px rail, stacking below the dashboard on narrower ones, with a scrolling transcript, a growing input, a thinking indicator while a reply is in flight, and one inline card per action the assistant executed.

Purpose: this project deliberately executes AI-initiated trades with no confirmation dialog. The entire mitigation for that choice is showing the user exactly what happened, immediately, in the transcript — so the confirmation cards are not decoration, they are the safety property.
Output: the chat wire types and api helpers, `ChatPanel`, `ChatActionCard`, and the layout dock.
</objective>

### Claude's-discretion choices made here

| Question (left open by `04-CONTEXT.md` / `04-UI-SPEC.md`) | Choice | Rationale |
|---|---|---|
| Whether the confirmation card is its own component file | Yes — `ChatActionCard.tsx` | It renders four combinations (trade or watchlist, succeeded or failed) with its own number formatting, and it is rendered from two places in the transcript loop. Inlining it would put a second formatting concern inside the panel's already substantial state machine |
| Whether the user's own sent message is rendered before the server confirms it | Yes, the user's message only — never an assistant message | The user's message is a fact the moment they send it, and `04-UI-SPEC.md` requires it to stay visible when a send fails. An optimistic *assistant* bubble would be inventing content, which is what `TradeBar`'s no-optimistic-fill discipline forbids and what the thinking indicator exists to avoid |
| What the panel does with the portfolio context after a trade executes through chat | Calls the shared portfolio context's `refresh()` when any action in a reply succeeded | The trade bar already refreshes after its own fill; a chat-initiated trade must move the header, the positions table, and the heatmap the same way, and `PortfolioProvider` already owns that fetch. Calling `refresh()` reuses it instead of adding a second fetch path |
| Whether collapse state is persisted | No | `04-UI-SPEC.md` resolved this explicitly: nothing in this phase's requirements asks collapse to survive a reload, only the conversation does, so no extra persistence mechanism is introduced for it |
| Input control shape | A growing `<textarea>` capped at roughly four visible lines, submitted by Enter with Shift+Enter for a newline | `04-UI-SPEC.md`'s long-text row requires a growing input with its own internal scroll. Enter-to-send matches `TradeBar`'s form-submit convention; Shift+Enter is what makes a multi-line draft possible at all once Enter is taken |
| Where the transcript's auto-scroll is triggered | On the message list changing and on the in-flight flag changing | Those are the only two moments new content enters the bottom of the transcript — a reply arriving and the thinking row appearing. Scrolling on every render would fight a user who has scrolled up to read |

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server response → rendered DOM | Model-generated prose and server-supplied error strings become page content |
| user keystrokes → `POST /api/chat` | Arbitrary typed text leaves the browser and becomes billable model input |
| conversation length → page layout | Unbounded content in a fixed region |
| click handlers → money-moving requests | A control whose press can execute a trade with no confirmation dialog |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-21 | Tampering | rendering assistant prose and server error strings into the DOM | high | mitigate | Every message body, action sentence, and error string is rendered as a plain text child, so React escapes it.
