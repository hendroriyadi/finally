# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Autonomous run: resolved directly against `planning/PLAN.md`, `04-CONTEXT.md`, and the already-approved
> `01-UI-SPEC.md`/`02-UI-SPEC.md`/`03-UI-SPEC.md` (this project's shipped, checker-approved design system
> baseline), per explicit user direction for an unattended build. This phase adds one new surface — the
> docked AI chat panel — and extends zero existing tokens; it reuses the established spacing scale,
> typography scale, 8-token color palette, and copywriting/error-string conventions verbatim.

Resolved: continue with plain Tailwind. Not blocking.

## Spacing Scale

Unchanged tokens from Phase 1/2/3 — no new values introduced:

| Token | Value | Usage this phase |
|-------|-------|-------------------|
| xs | 4px | Gap between a message's role label ("YOU" / "FINALLY") and its bubble; icon-to-text gap inside inline action-confirmation cards; gap between stacked confirmation cards when a single reply executes more than one action |
| sm | 8px | Message bubble internal padding (`px-3 py-2`); gap between consecutive messages; message-input row internal padding, matching `TradeBar`'s `px-2 py-1` input sizing |
| md | 16px | Chat panel internal padding (header row, transcript container, input row all use `md` external padding, matching every other panel shell's `px-4 py-3` header convention); gap between the transcript's bottom and the input row |
| lg | 24px | Gap between the existing two-column dashboard grid and the docked chat panel on desktop — same `lg` gap Phase 3 already uses between its own left/right columns, extended to the new third region |
| xl | 32px | Outer page margin on desktop (unchanged) |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions: the chat panel's **collapsed rail width is 56px** (a layout dimension, not a spacing token, but declared here for completeness — it is a multiple of 4). This gives the single reopen icon button a centered 56px×56px hit target well above the 44px minimum already established as this project's touch-target floor (`01-UI-SPEC.md`'s remove-ticker-button exception), without the rail competing visually with the 384px expanded panel width.

Unchanged 8-token set from `frontend/app/globals.css` — this phase adds no new colors, only new *usages*:

| Role | Value | New usage this phase |
|------|-------|------------------------|
| Dominant (60%) | `#0d1117` | Assistant message bubble fill (`bg-canvas`, bordered `border-edge`) — assistant replies read as neutral "system voice" content, same surface tone as the page itself |
| Secondary (30%) | `#1a1a2e` | Chat panel shell surface (`bg-panel`, matching every other panel's `rounded-md border border-edge bg-panel`); collapsed-rail surface |
| Accent (10%) | `#ecad0a` | Focus ring on the message-input textarea and the collapse-toggle button (unchanged reservation — focus rings only, same as every other input in this app). **No new accent usage beyond focus rings** — the 10%-reserved contract is unchanged, not diluted, matching Phase 3's explicit precedent of adding a new surface without touching the accent budget |
| Positive | `#22c55e` | Inline confirmation card border/icon for a successful AI-executed **buy** or a successful watchlist **add** (`CheckCircle2` icon, `border-positive/40` card border, `bg-positive/10` card fill — a wash, never a saturated block, per the line-chart-area-wash precedent in `03-UI-SPEC.md`) |
| Destructive | `#ef4444` | Inline confirmation card border/icon for a **failed** AI-initiated action (`AlertCircle` icon, `border-destructive/40`, `bg-destructive/10`) — used identically regardless of whether the action was a buy/sell or a watchlist change; also the send-message inline error text below the input, matching `TradeBar`/`AddTickerForm`'s `role="alert" text-destructive` pattern exactly |
| Primary | `#209dd7` | User message bubble tint (`bg-primary/15`, `border-primary/30`) — Primary blue already carries an "this is you / this is live data" meaning app-wide (ticker-symbol emphasis in `PositionsTable`, all price-series line strokes); reusing it at low opacity to distinguish the user's own messages from assistant messages is an extension of that existing meaning, not a new one. Right-aligned bubbles use this tint; left-aligned assistant bubbles use the neutral Dominant/Secondary treatment above |
| Submit | `#753991` | Send-message button fill (`bg-submit`) — the send button is a form-submit action exactly like `AddTickerForm`'s "Add Ticker" button, so it reuses the same reserved purple rather than introducing a second submit color |
| Border (neutral) | `#30363d` | Chat panel outer border; message bubble borders; divider between the transcript and the input row; collapsed-rail border |

**Selling P&L color note:** a **sell** confirmation is still a successful action (Positive/green), never colored by whether the trade itself was profitable — action-success and trade-profitability are two different signals and this phase does not conflate them. Profitability is already visible in the positions table/heatmap; the chat confirmation only answers "did this instruction execute."

**No new accent dilution:** consistent with Phase 3's explicit note, this phase introduces zero new accent (`#ecad0a`) usage beyond the standard focus-ring convention already established in Phase 1.

## Visual Hierarchy

Primary focal point (this phase, within the new chat panel): the **message-input row** (textarea + Submit-purple send button) — it's the one new always-visible call to action, framed by the Accent focus ring exactly like every other input in this app, and it is what turns the panel from a read-only transcript into the phase's headline "converse with an AI that trades for you" interaction.

Secondary focal point: **inline action-confirmation cards** — when present, they are the most information-dense and highest-stakes new visual element in the app (they represent real money movements and watchlist changes executed with zero confirmation dialog), so they get the Positive/Destructive wash treatment and Display-weight dollar figures to stand out clearly from surrounding prose, without using a third color that would compete with the app's existing green/red profit-and-loss vocabulary.

Tertiary: the **message transcript** itself (role labels, bubble text) — supporting context for the input row and confirmation cards, styled at Body/Label sizes with no special emphasis, matching how `WatchlistPanel` and `PositionsTable` keep their row text at the same restrained weight as everything else on the page.

Existing surfaces (header, trade bar, positions table, watchlist grid, detail chart, heatmap, P&L chart) keep their established Phase 1/2/3 visual weight completely unchanged — this phase adds a new docked region alongside them, it does not resize, restyle, or visually compete with the existing dashboard for attention. When the chat panel is collapsed, the dashboard occupies its full previous width exactly as it did before this phase existed.

**Layout contract** (new this phase — the chat panel must slot in without disturbing `app/page.tsx`'s existing two-column grid):

- **Mount point:** `ChatPanel` renders in `app/layout.tsx`, as a sibling to `{children}` below `AppHeader` — a page-spanning dock, consistent with `AppHeader`'s own page-spanning placement and with `04-CONTEXT.md`'s discretion note leaning toward layout-level. `layout.tsx`'s body becomes a `flex-col` (header) over a `flex-1 flex-row` region containing `{children}` (the existing dashboard, unchanged, still independently `mx-auto max-w-screen-2xl`-constrained within its own flex-1 area) and `ChatPanel` docked at the row's end.
- **Desktop (≥1280px, matching Phase 3's `xl` breakpoint):** `ChatPanel` is a fixed-width **384px** (`w-96`) right-docked sidebar, full remaining viewport height below the header, with its own internal scroll for the transcript (the page itself never scrolls past the header/dashboard's existing behavior). Separated from the dashboard by the `lg` (24px) gap. Collapsing it shrinks it to the 56px rail described in Spacing Scale; the dashboard reflows to reclaim the freed width (it is a normal flex sibling, not an overlay).
- **Narrower / tablet (<1280px):** `ChatPanel` drops from a side-dock to a **full-width panel stacked below** the dashboard content, matching Phase 3's established "right column drops below on narrow viewports" convention — it does not attempt a slide-over/overlay behavior, keeping this phase's interaction model identical at every breakpoint (docked, collapsible, never modal).
- **Collapse mechanism:** a single toggle button (`PanelRightClose` when expanded / `PanelRightOpen` when collapsed) in the panel's header row, top corner. Collapsing/expanding is instant (no animation requirement beyond a simple width transition) and is **component-local state, not persisted** — the panel returns to its default expanded state on every page load. This is a deliberate, minimal choice: nothing in CHAT-01–07 requires collapse state to survive a refresh (only the conversation itself must, per CHAT-01), so no additional persistence mechanism is introduced for it.
- **State ownership:** `ChatPanel` owns its own message list, input value, loading flag, and collapse flag via component-local `useState` — no new context/provider. `04-CONTEXT.md` already reasons this through: the chat panel is a single component subtree with no sibling needing chat state, unlike `PortfolioProvider`/`PriceStreamProvider`, which have multiple independent consumers spanning `layout.tsx`/`page.tsx`.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Panel title | "AI Copilot" |
| Primary CTA | "Send message" (icon-only `Send` button in the compact input row; `aria-label="Send message"`, matching the accessible-name convention every icon-only control in this app already uses) |
| Collapse toggle (expanded → collapsed) | `aria-label="Collapse chat panel"` |
| Collapse toggle (collapsed → expanded) | `aria-label="Expand chat panel"` |
| Empty state heading (no conversation yet) | "Start chatting with FinAlly" |
| Empty state body | "Ask about your portfolio, or tell FinAlly to buy, sell, or update your watchlist." |
| Loading state (message sent, awaiting reply) | "FinAlly is thinking…" — a small `Loader2`-spinner row appended below the user's just-sent message, removed the instant the real reply arrives. This is a status indicator, not a fake assistant bubble — no optimistic assistant content is ever rendered (matching `TradeBar`'s "no optimistic fill" discipline, per `04-CONTEXT.md`) |
| History load error (panel mount) | "Couldn't load your conversation — check your connection and reload." |
| Send failure (the `POST /api/chat` request itself fails — network/5xx, distinct from a graceful assistant reply) | "Couldn't reach FinAlly — check your connection and try again." (inline, `role="alert"`, below the input row — the user's own optimistically-rendered message stays visible; it is never rolled back) |
| Malformed/unparseable model output (CHAT-06, returned as a normal graceful assistant reply per backend contract) | Rendered as a completely ordinary assistant message bubble containing whatever graceful text the backend returned (e.g. "I had trouble processing that — could you rephrase?") — no special error styling, because from the frontend's perspective this is a successful `200` response with a normal message, not a client-visible error state |
| Inline trade confirmation — success (buy) | "Bought {qty} {TICKER} at ${price}" (qty formatted via the existing trimmed-decimal convention from `PositionsTable.formatQuantity`; price via `formatCurrency`, 2 decimals) |
| Inline trade confirmation — success (sell) | "Sold {qty} {TICKER} at ${price}" |
| Inline trade confirmation — failure | The backend's own per-action human-readable error string, rendered verbatim (e.g. "Couldn't buy 50 TSLA — insufficient cash.", mirroring `TradeBar`'s exact error phrasing so a rejection reads identically whether it came from the trade bar or from chat) |
| Inline watchlist confirmation — success (add) | "Added {TICKER} to your watchlist." |
| Inline watchlist confirmation — success (remove) | "Removed {TICKER} from your watchlist." |
| Inline watchlist confirmation — failure | The backend's own per-action error string, rendered verbatim (e.g. "Couldn't add {TICKER} — check the symbol and try again.", matching `AddTickerForm`'s exact phrasing) |
| Destructive confirmation | Not applicable — zero-confirmation auto-execution is a deliberate, locked design decision (PLAN.md §9, reaffirmed in `04-CONTEXT.md`'s "Specifics"). The transparency mitigation is the inline confirmation shown immediately **after** execution (CHAT-05), never a pre-execution confirmation dialog, for either trades or watchlist changes, consistent with Phase 1's identical resolution for the manual remove-ticker control |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Elements classified for this phase: `chat-transcript` (list-collection), `message-input-form` (form), `inline-action-confirmation` (static-content, rendered per action within a transcript entry), `collapse-toggle` (interactive-control).

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | chat-transcript | ✅ covered | Zero messages (first-ever visit, or a fresh backend with no `chat_messages` rows) renders the "Start chatting with FinAlly" heading + body (Copywriting Contract) in place of the transcript, not a blank scroll area. |
| loading | chat-transcript | ✅ covered | On panel mount, before `GET /api/chat/history` resolves, the transcript area shows the same pulsing-skeleton row treatment `PositionsTable`/`WatchlistPanel` already use, rather than a blank panel; while awaiting an assistant reply after sending, the transient "FinAlly is thinking…" row (Copywriting Contract) appears below the just-sent user message — never an optimistic fake assistant bubble. |
| error | chat-transcript | ✅ covered | A failed `GET /api/chat/history` shows the history-load-error copy (Copywriting Contract) in place of the transcript; a failed `POST /api/chat` (network/5xx) leaves the user's own message visible and shows the send-failure copy inline below the input, never silently dropping the user's typed message. |
| populated | chat-transcript | ✅ covered | User messages render right-aligned in a Primary-tinted bubble; assistant messages render left-aligned in a neutral (Dominant-surface) bubble; each carries a small role label above it. Conversation persists across a page refresh by re-fetching `GET /api/chat/history` on mount (CHAT-01). |
| partial | inline-action-confirmation | ✅ covered | A single assistant reply that executes more than one action (e.g. two trades, or a trade plus a watchlist change) renders one confirmation card per action, stacked with `xs` gap, each independently colored success/failure — a partial success (one action succeeds, another in the same reply fails) is fully representable since every card's status is independent, never an all-or-nothing indicator for the whole reply. |
| zero-one-many | inline-action-confirmation | ✅ covered | A reply with zero `trades`/`watchlist_changes` renders no confirmation cards at all (just the assistant's prose); one action renders one card; many actions render a stacked list — no separate layout needed for any count. |
| overflow | chat-transcript | ✅ covered | The transcript is a bounded-height (`flex-1 min-h-0`) internally-scrolling container, matching `PositionsTable`'s bounded-scroll pattern, and auto-scrolls to the newest message on send/receive; a long conversation history scrolls internally rather than growing the panel or the page. |
| long-text | message-input-form | ✅ covered | The input is a growing textarea (not a single-line input, unlike `TradeBar`'s ticker/quantity fields) capped at a maximum visible height (e.g. ~4 lines) with its own internal scroll beyond that — a long pasted message never pushes the send button off-panel or reflows the page. |
| long-text | chat-transcript | ✅ covered | Long assistant or user messages wrap normally within their bubble at Body line-height (1.5); the bubble grows vertically to fit — text is never truncated or clipped. |
| overflow / zero-one-many | collapse-toggle | ✅ covered | The toggle has exactly two states (expanded/collapsed) with no intermediate state; collapsing never loses in-progress transcript state or an unsent draft in the input — both are preserved in the same component-local state and simply become visually hidden until re-expanded. |

Applicable state considerations resolved: 9 covered, 0 backstop, 0 unresolved.
