<objective>
Let the assistant curate the watchlist — and make sure a ticker it adds actually starts streaming.

`04-RESEARCH.md`'s Pitfall 2 is the reason this is its own plan rather than four lines appended to the action loop. The watchlist data-access functions only touch a table; what makes a ticker *live* is a second call to the running market source, plus a compensating rollback if that call fails. A chat route that called only the first half would produce the worst kind of bug: the database says the ticker was added, the grid shows the row, and the price cell stays empty until someone restarts the backend.

Task 1 makes that sequence exist exactly once, as two importable helpers, with the manual endpoints re-pointed at them and their public behaviour unchanged. Task 2 gives the assistant the same two calls.

Purpose: two independent copies of a persist-then-track-then-compensate sequence is how the database and the live stream drift apart. One copy with two callers cannot.
Output: the extracted helpers and their error types, the chat watchlist executor, and tests on both sides.
</objective>

### Claude's-discretion choices made here

| Question (left open by `04-CONTEXT.md` / `04-RESEARCH.md`) | Choice | Rationale |
|---|---|---|
| Where the shared add/remove sequence lives | Two module-level async helpers in `backend/app/routes/watchlist.py`, imported by `app/routes/chat.py` | `04-RESEARCH.md` recommends factoring the shared logic out but not where to. This codebase already has a route module importing from another route module — `app/routes/portfolio.py` imports `normalize_ticker` from here — so keeping the helpers beside the pattern and the cap constant they belong to introduces no new layout convention. Inventing a `services/` package for two functions would be a bigger change than the one being made |
| What the helpers raise | Purpose-named exceptions (`DuplicateTickerError`, `TickerNotOnWatchlistError`, `MarketSourceSyncError`) plus the existing `WatchlistCapReachedError`, never `HTTPException` | The two callers need opposite things from a failure: the HTTP handler needs a status code, the chat executor needs a sentence to show in a transcript. A helper that raised an HTTP error object would force the chat side to catch and unwrap a web-framework type to build a chat message — which is exactly the coupling `04-RESEARCH.md`'s Pitfall 1 warns about, one layer further in |
| Whether the manual endpoints' behaviour may change | No — every status code and every detail string is preserved exactly | The refactor's whole value is that it is invisible from outside. The existing route test file is the proof, and it passes unmodified |
| Whether the chat executor calls `normalize_ticker` itself or lets the helpers do it | The executor calls it, inside its own try/except, before calling a helper | It mirrors the HTTP handlers, which also normalize before calling in. Keeping normalization out of the helpers means the helpers take an already-valid ticker and have exactly one reason to fail per branch, and it keeps the `HTTPException` that `normalize_ticker` raises confined to the two places already prepared to catch it |
| Error copy for a failed AI watchlist action | The exact strings the manual UI already shows: `Couldn't add {TICKER} — check the symbol and try again.` and `Couldn't remove {TICKER} — try again.` | `04-UI-SPEC.md`'s copy contract says a failure must read identically whether it came from the form or from chat. These are the literal strings in `AddTickerForm.tsx` and `RemoveTickerButton.tsx` today |
