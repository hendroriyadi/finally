<objective>
Give the assistant a memory and a view. Plan 04-01 proved a model reply can move real money; it did so blind — the model was told nothing about the portfolio it was trading, and nothing it said was written down.

This plan closes both gaps. Task 1 makes the conversation durable: a new `app/db/chat.py` writes the two rows every turn produces and reads them back through a bounded endpoint the browser calls on mount. Task 2 makes the assistant informed: the same read pair the portfolio route and the snapshot writer already use is called fresh on every request, so the model answers about the cash, holdings, and prices that exist right now rather than the ones that existed when the conversation started.

Purpose: "portfolio-aware" is the load-bearing adjective in this phase's goal, and it is only true if the context is re-read per turn. A cached context would be right for exactly one message and quietly wrong for every one after it.
Output: `app/db/chat.py`, both persistence call sites, `GET /api/chat/history`, the grounded prompt builder, and two extended test files.
</objective>

### Claude's-discretion choices made here

| Question (left open by `04-CONTEXT.md` / `04-RESEARCH.md`) | Choice | Rationale |
|---|---|---|
| How many prior messages to send to the model | `MAX_CONTEXT_MESSAGES = 20` rows, and the same constant bounds the history endpoint | CONTEXT.md grants roughly ten turns of discretion; a turn is a user message plus an assistant reply, so ten turns is twenty rows (`04-RESEARCH.md` Assumption A2). One constant serving both the prompt and the endpoint is what CONTEXT.md's "reuse the same recent-history query" asks for, and it means there is no second, uncapped read path into this table |
| Whether the history endpoint takes a `limit` or `since` parameter | No parameters at all | Identical reasoning to Plan 03-01's history endpoint: an endpoint with no client-controlled input has nothing to validate and nothing to fuzz, and a fixed server-side cap removes the input surface instead of guarding it (T-04-10) |
| History wire shape | `{"messages": [...]}` | Matches this codebase's two existing envelopes, `{"tickers": [...]}` and `{"snapshots": [...]}`. No endpoint in this project returns a bare top-level array |
| Where the new user message is persisted relative to the history read | Read history first, then write the user's row, then build the prompt from that history plus the new message | Reading after writing would hand the model the current message twice — once as history and once as the message being answered — which reads to a model as the user repeating themselves. Writing before the model call rather than after means a turn whose model call fails still leaves a record of what was asked |
| What the actions column holds for each role | SQL `NULL` for a user row; a JSON array — possibly empty — for an assistant row | An empty array is a real statement ("this reply executed nothing"), which is different from "actions do not apply to this kind of row". Collapsing both to `NULL` would lose that distinction the moment the transcript is re-rendered |
| Prompt assembly shape | One system message carrying the persona and the rules, one system message carrying the rendered portfolio and watchlist snapshot, then the history messages in role order, then the new user message | Keeping the volatile context in its own message rather than concatenating it into the persona makes the "is this fresh?" question answerable by looking at one string, and keeps the persona text identical across every turn |
| Whether the context builder is reachable from a test without a live model call | Yes — `build_chat_messages(...)` is a module-level pure function taking already-loaded data | `04-VALIDATION.md`'s CHAT-02 row asks for assertions on the builder's output rather than on a live call. A pure function with explicit inputs is testable in one line and cannot accidentally acquire a hidden read |
